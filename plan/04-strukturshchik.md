# Агент-структурщик

## Назначение

Структурщик превращает бриф и пакет фактуры в план материала. Он не пишет статью, не добавляет новые факты и не придумывает инфографику. Его работа — выбрать состав блоков, порядок чтения, назначение каждого блока и факты, на которых блок обязан стоять.

Главная цель: дать писателю не тему, а редакционную конструкцию, в которой каждый раздел отвечает на реальный вопрос пользователя и опирается на проверяемую фактуру.

## Источники правил

- `handoff-konveyer/02-format.md` — итоговый формат `{ meta, blocks }`.
- `handoff-konveyer/03-bloki.md` — меню доступных блоков.
- `handoff-konveyer/04-kachestvo.md` — машинные проверки и требования к содержанию.
- `handoff-konveyer/05-fakty.md` — правила фактов.
- `handoff-konveyer/07-promty.md` — промпт структурщика.
- `handoff-konveyer/limity.json` — лимиты и список типов блоков.
- `handoff-konveyer/fakty/*.json` — темы, продукт, кейсы, конкуренты, термины, глоссарий, внутренние ссылки.

## Вход

Структурщик получает:

- `PipelineRequest`.
- `FactPackage` после машинной приемки фактов.
- `ProjectKnowledge` или релевантный срез `fakty/*.json`.
- `LIMITS` из `limity.json`.
- `BLOCK_TYPES` из `limity.json`.
- Список внутренних ссылок, допустимых для материала.
- Для темы из очереди: slug, URL, question, cluster, demand, wave.

## Выход

Структурщик возвращает `MaterialStructure`.

Минимальная форма:

```json
{
  "requestId": "A-0001",
  "materialKind": "guide",
  "title": "Какие бывают техники продаж и какая работает в холодном звонке?",
  "seoTitle": "Техники продаж: какие бывают и что работает в звонке",
  "description": "Разбираем техники продаж, где они помогают, где ломаются и как тренировать менеджеров на звонках.",
  "requiredBlocks": ["lead", "tldr", "prose", "points", "steps", "faq", "cta"],
  "sections": [
    {
      "id": "lead",
      "blockType": "lead",
      "purpose": "Ответить на главный вопрос целиком в 200-450 знаков.",
      "requiredClaimIds": ["F1", "F3"],
      "targetWords": 70
    }
  ],
  "createdAt": "2026-08-09T00:00:00.000Z"
}
```

## Правила структуры

- `lead` всегда первый и ровно один.
- Структура отвечает на один вопрос. Если в брифе два вопроса, структурщик возвращает проблему, а не склеивает два материала.
- Заголовки смысловых блоков несут предмет. Вопросная форма допустима, но не обязательна: ее стоит использовать только там, где это звучит как живой вопрос читателя.
- Перевернутая пирамида: лид отвечает на вопрос целиком, дальше идут детали по убыванию важности.
- Каждый смысловой раздел должен иметь хотя бы один `requiredClaimIds`.
- Раздел без фактуры не планируется. Если раздел нужен, но факта нет, структурщик возвращает `missingFacts`/ошибку фактуры.
- В структуре обязательно есть блок или раздел про границы применимости: когда подход не подходит, чего не решает, где нужны данные или проверка.
- FAQ обязателен для всех материалов и планируется минимум на 8 вопросов.
- `related` желателен, но только с внутренними ссылками из `vnutrennie-ssylki.json`.
- `cta` один и стоит в конце. Оффер выбирается под конкретную тему, а не из общего дефолта.
- `sources` обязателен, если в фактуре есть claims о чужих продуктах или внешних источниках, которые должны быть защищены датой снимка.

## Выбор блоков

Структурщик выбирает блок по содержанию, а не ради разнообразия.

- `lead` — всегда первый ответ.
- `tldr` — если материал сложный и полезно дать 3-5 коротких выводов.
- `prose` — базовый вопрос-ответный раздел.
- `points` — критерии выбора, признаки, ошибки, требования.
- `steps` — процесс или инструкция; от трех шагов сайт может собрать HowTo.
- `table` — данные, сравнение, матрица решений; для `compare` очень желателен.
- `stats` — только если числа есть во входной фактуре.
- `matrix` — если есть два измерения выбора.
- `cards` — подборки сервисов, сценариев, типов или кейсов.
- `fork` — развилка кому что подходит; обязателен для `compare`.
- `verdict` — финальный выбор; обязателен для `compare`.
- `quote` — только если есть атрибутируемая цитата.
- `callout` — особенно для news: что это значит для продаж, обучения, найма или сервиса.
- `promo` — внутренняя врезка, если она не ломает чтение.
- `related` — минимум две внутренние ссылки, без ссылки на сам материал.
- `faq` — реальные вопросы после чтения, не пересказ разделов.
- `sources` — источники с датой снимка.
- `cta` — финальное действие, которое логично следует из вопроса материала.

## Обязательные каркасы по типам

### `guide`

Базовый каркас:

```text
lead -> tldr? -> prose -> points/steps -> prose/callout -> related? -> faq -> cta
```

Обязательно:

- главный ответ в `lead`;
- 3-6 смысловых разделов;
- раздел про границы применимости;
- FAQ 8+;
- CTA.

### `compare`

Базовый каркас:

```text
lead -> tldr -> prose -> table -> points/steps -> fork -> verdict -> sources -> related? -> faq -> cta
```

Обязательно:

- `table`;
- `fork`;
- в `fork` должен быть вариант `neither`;
- `verdict`;
- `sources`;
- FAQ 8+;
- CTA.

### `news`

Базовый каркас:

```text
lead -> prose -> quote? -> callout -> related? -> faq? -> cta
```

Обязательно:

- первоисточник события;
- дата события или публикации;
- блок добавленной ценности, например `callout`: что это значит для отдела продаж, обучения, найма или клиентского сервиса;
- не пересказывать пресс-релиз без собственного вывода.

## Что структурщик не делает

- Не пишет полный текст блоков.
- Не формулирует финальные FAQ-ответы.
- Не придумывает факты, числа, кейсы, тарифы, юридические выводы.
- Не ищет новые источники.
- Не использует блоки вне `BLOCK_TYPES`.
- Не добавляет декоративные визуалы.
- Не пишет HTML или Markdown.

## Когда возвращать в `needs_facts`

Структурщик должен вернуть материал оркестратору на фактуру, если:

- для обязательного раздела нет `requiredClaimIds`;
- в теме нужен юридический, рыночный или методический факт, а поисковик его не нашел;
- для claims о чужом продукте нет источника и даты снимка;
- продуктовая возможность Lexis Voice нужна для тезиса, но ее нет в `produkt.json`;
- кейсовая цифра нужна для вывода, но ее нет в `keysy.json`;
- тема сравнения требует данных о продукте, которого нет в `konkurenty.json` и который поисковик не подтвердил официальным сайтом.

## Машинная приемка структуры

До писателя структура должна пройти проверку:

- все `blockType` входят в `BLOCK_TYPES`;
- `lead` есть, он первый и один;
- для `compare` есть `table`, `fork`, `verdict`, `faq`, `cta`;
- для `compare` запланирован `fork.neither` или явно указан constraint для него;
- FAQ запланирован минимум на 8 вопросов;
- каждый смысловой section содержит `purpose` и `requiredClaimIds`;
- каждый `requiredClaimIds` существует в `FactPackage`;
- `seoTitle <= 65`, `description <= 160`;
- суммарный `targetWords` не ниже 1200;
- нет блоков без назначения.

## Промпт структурщика

Системная часть должна включать ядро из `07-promty.md` и роль структурщика:

```text
Роль: выпускающий редактор. Ты проектируешь состав материала.

Вход: бриф + каталог блоков + фактура.
Выход: JSON MaterialStructure без полного текста.

Правила:
- Перевернутая пирамида: лид отвечает на вопрос целиком, дальше детали по убыванию важности.
- Заголовки несут предмет; вопросы используются только там, где человек действительно так спрашивает.
- В каждом разделе хотя бы один проверяемый факт: число, срок, механика, ограничение.
- Обязателен раздел про границы.
- Блоки выбираются по содержанию: критерии -> points, процесс -> steps, данные -> table, развилка -> fork.
- Структура не повторяет соседний материал.
- Для kind=compare обязательны fork с neither и verdict.
- Для всех материалов FAQ 8+.
```

## Правило для CTA

Дефолтного CTA нет: каждая статья отвечает на свой вопрос и ведет к своему следующему действию. Структурщик сам выбирает смысл CTA по теме, но обязан привязать его к фактуре и продуктовой области.

Примеры направления, а не шаблоны:

- материал про тренировки менеджеров может вести к голосовому тренажеру продаж;
- материал про найм может вести к оценке кандидатов или тест-звонку;
- материал про контроль качества может вести к разбору реальных звонков и чек-листам;
- материал про интеграции может вести к обсуждению CRM/телефонии/API;
- новость может вести к короткой консультации по применимости события для отдела продаж, обучения, найма или сервиса.

Структурщик не пишет финальный продающий текст CTA за писателя. Он указывает `purpose`, желаемое действие и продуктовый контекст. Если во входной фактуре нет подтверждения нужной возможности Lexis Voice, CTA должен быть более общим или материал возвращается в `needs_facts`.
