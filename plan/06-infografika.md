# Агент-инфографик

## Назначение

Инфографик — редактор данных для визуальных блоков. Он не рисует картинки и не генерирует изображения. Он проверяет, какие визуальные элементы можно вывести из уже написанного материала и фактуры, дозаполняет структурированные данные там, где это безопасно, и отказывается от визуала там, где данных не хватает.

Главное правило: визуал должен быть производным от данных. Если визуал нельзя проверить по данным материала, он не нужен.

## Источники правил

- `handoff-konveyer/02-format.md` — что сайт выводит автоматически из блоков.
- `handoff-konveyer/03-bloki.md` — какие блоки дают визуальные данные.
- `handoff-konveyer/04-kachestvo.md` — машинные проверки.
- `handoff-konveyer/07-promty.md` — промпт инфографика.
- `handoff-konveyer/fakty/*.json` — разрешенные цифры, кейсы, продуктовые факты и источники.

## Вход

Инфографик получает:

- `PipelineRequest`.
- `FactPackage`.
- `MaterialStructure`.
- `DraftDoc` после писателя.
- `ProjectKnowledge` или релевантный срез `fakty/*.json`.
- Список разрешенных типов визуальных блоков.

## Выход

Инфографик возвращает не картинку, а структурированный отчет:

```json
{
  "requestId": "A-0001",
  "visuals": [
    {
      "id": "V1",
      "kind": "hero_compare",
      "status": "derivable",
      "sourceBlockId": "classification-table",
      "reason": "Таблица содержит критерий и две стороны сравнения, минимум три строки.",
      "sourceClaimIds": ["F1", "F4"]
    }
  ],
  "patches": [
    {
      "blockId": "classification-table",
      "what": "Сократить формулировки в ячейках и сделать колонки параллельными.",
      "owner": "writer"
    }
  ],
  "missingData": [
    {
      "visualKind": "stats_strip",
      "need": "Нет опубликованной цифры по росту конверсии, плашку не строить."
    }
  ]
}
```

В коде первой версии это может нормализоваться в текущий `InfographicSpec[]`, но агент должен мыслить шире: `visuals`, `patches`, `missingData`.

## Что делает агент

- Проверяет, какие блоки уже пригодны для визуального вывода.
- Проверяет таблицы и матрицы: есть ли структура данных, достаточно ли строк, параллельны ли формулировки.
- Проверяет `steps`: есть ли минимум три шага, у каждого есть действие и результат.
- Проверяет `stats`: все ли числа есть во входной фактуре и разрешены к публикации.
- Проверяет `fork`: есть ли разные варианты выбора и, для compare, `neither`.
- Проверяет `cards`: есть ли единая структура карточек, чтобы они не превратились в простыню текста.
- Предлагает минимальные правки данных, если визуал можно вывести после безопасной нормализации.
- Указывает, каких данных не хватает, если визуал невозможен.

## Что агент не делает

- Не создает изображения.
- Не придумывает диаграммы для красоты.
- Не добавляет факты, числа, строки таблиц или кейсы, которых нет в фактуре.
- Не дублирует соседний текст декоративной карточкой.
- Не меняет смысл материала.
- Не переписывает весь блок вместо писателя.
- Не использует внешние ссылки или источники.

## Какие визуалы допустимы

### `visual_slot`

Источник: любой блок с достаточно структурированными данными: `table`, `matrix`, `steps`, `stats`, `fork`, `cards`, `points`.

Идея: это место под красивую кастомную инфографику, похожее по свободе на zero-block. Агент может предложить не шаблонный визуал, а отдельный визуальный слот с brief для дизайна.

Ограничение: свобода композиции не означает свободу фактов.

Практический смысл: в статье остается не просто стандартный блок `table` или `steps`, а отдельное место под выразительную визуальную сцену. Ее можно отрисовать кодом, дизайнерским компонентом или следующим агентом, но только по контракту данных. Так мы можем делать материалы красивыми и авторскими, не превращая инфографику в генератор выдуманных цифр.

Условия:

- у слота есть `sourceBlockId`;
- у слота есть `sourceClaimIds`;
- у слота есть `dataContract`: какие данные можно использовать;
- у слота есть `allowedData`: какие поля исходного блока можно брать в рендер;
- у слота есть `forbiddenAdditions`: что нельзя добавлять даже ради красивой композиции;
- у слота есть `visualGoal` и `tone`, чтобы будущий рендерер понимал смысл визуала;
- в слоте нельзя добавлять новые числа, продукты, цены, сравнения или обещания;
- дизайн может быть свободным: сетка, композиция, акценты, порядок элементов, но подписи и значения должны быть выводимы из данных.

Пример:

```json
{
  "kind": "visual_slot",
  "renderMode": "custom_visual_slot",
  "sourceBlockId": "classification-table",
  "visualSlot": {
    "placement": "after_block",
    "afterBlockId": "classification-table",
    "brief": "Показать уровни техник продаж как карту: методология -> этап звонка -> речевой прием -> тренируемое действие.",
    "dataContract": [
      "Использовать только строки и подписи из sourceBlockId.",
      "Не добавлять новые техники продаж.",
      "Не добавлять числа и обещания эффективности."
    ],
    "allowedData": ["head", "rows"],
    "forbiddenAdditions": ["новые факты", "новые числа", "новые продукты", "обещания эффективности"],
    "visualGoal": "Быстро показать читателю, что техники продаж отличаются уровнем применения, а не являются взаимозаменяемыми списками приемов.",
    "tone": "editorial",
    "designFreedom": "custom_composition"
  }
}
```

### `hero_compare`

Источник: `table` или `matrix`.

Условия:

- минимум три строки;
- есть критерий и стороны сравнения;
- формулировки в колонках короткие и параллельные;
- данные не являются декоративным пересказом текста.

### `howto_steps`

Источник: `steps`.

Условия:

- минимум три шага;
- каждый шаг содержит действие;
- желательно есть ожидаемый результат;
- шаги идут в реальном порядке выполнения.

### `decision_fork`

Источник: `fork`.

Условия:

- есть 2+ варианта;
- у каждого варианта есть условия выбора;
- для `compare` есть `neither`;
- развилка не подменяет verdict.

### `stats_strip`

Источник: `stats`, `keysy.json`, `produkt.json` или числовые claims.

Условия:

- каждое число опубликовано во входной фактуре;
- число не округлено и не пересчитано моделью;
- рядом есть контекст: период, база, единица измерения.

### `cards_grid`

Источник: `cards`.

Условия:

- у карточек одинаковые поля;
- карточки сравнимы между собой;
- нет ручной оценки без факта.

### `criteria_points`

Источник: `points`.

Условия:

- пункты являются критериями, признаками или ошибками;
- каждый пункт короткий;
- пункт не дублирует соседний prose.

## Когда визуал запрещен

- Нет структурированных данных.
- Есть только общий текст без чисел, критериев, шагов или вариантов выбора.
- Число нужно придумать, округлить или вывести из воздуха.
- Визуал повторяет то, что уже сказано рядом.
- Данные опираются на claims с `confidence: low` или claims, не разрешенные в финальном тексте.
- Для конкурентов нет источника и даты снимка.
- Для продукта Lexis Voice нет подтверждения в `produkt.json` или `keysy.json`.

## Правки блоков

Инфографик может предложить только локальные правки данных:

- укоротить ячейки таблицы;
- сделать формулировки колонок параллельными;
- добавить недостающее поле `note`, если оно выводится из уже имеющегося claim;
- привести шаги к единой форме;
- вынести число в `stats`, если оно уже есть в фактуре;
- убрать визуальный статус, если данных недостаточно.

Правки не должны добавлять новый смысл. Если для правки нужен новый факт, агент пишет `missingData`, а не правит блок.

## Машинная приемка инфографики

Перед следующим этапом нужно проверить:

- каждый visual ссылается на существующий block id;
- каждый `sourceClaimIds` существует в `FactPackage`;
- `stats_strip` содержит только числа из фактуры;
- `hero_compare` строится только из `table`/`matrix` с 3+ строками;
- `howto_steps` строится только из `steps` с 3+ шагами;
- `decision_fork` строится только из `fork`;
- нет visual со статусом `derivable`, если источник данных пустой;
- `missingData` не блокирует материал, если визуал необязателен.

## Когда возвращать задачу

В `needs_writer_revision`:

- таблица пригодна для визуала, но формулировки слишком длинные или разные по форме;
- `steps` есть, но шаги не содержат действий;
- `cards` есть, но карточки имеют разные поля;
- визуал дублирует текст рядом и лучше убрать/перенести блок.

В `needs_facts`:

- запланирован `stats_strip`, но числа не подтверждены фактурой;
- визуал требует продуктовую цифру или кейс, которого нет в `keysy.json`;
- визуал требует факт о другом продукте без источника и даты снимка.

## Промпт инфографика

Системная часть должна включать роль из `07-promty.md`:

```text
Роль: редактор данных. Ты не создаёшь изображений и не пишешь текст.

Вход: заполненный материал.
Выход: правки блоков + список того, чего не хватает.

Что делаешь:
- Проверяешь, что таблица сравнения даёт заглавную инфографику.
- Формулировки в ячейках делаешь короткими и параллельными.
- Цифры в плашках берёшь только из фактуры и только те, что уже опубликованы.
- Если данных на визуал не хватает, пишешь, какого поля недостаёт.

Чего не делаешь:
- не добавляешь диаграмм для наглядности;
- не дублируешь визуалом то, что уже сказано текстом рядом;
- не придумываешь ни строку, ни число.
```

## Решение для первой версии

Для первой реализации можно не вызывать LLM. Большую часть работы инфографика можно сделать детерминированно:

- найти `table`/`matrix` с 3+ строками;
- найти `steps` с 3+ шагами;
- найти `fork`;
- найти `stats`;
- вернуть `InfographicSpec[]`.

LLM-инфографик понадобится позже, когда нужно будет аккуратно предлагать локальные правки таблиц и шагов без переписывания материала.

## Решение для второй версии

Реальный `NeuromediaInfographicsAgent` уже можно подключать после писателя:

- детерминированный слой находит все потенциально выводимые визуалы;
- LLM-слой выбирает не все подряд, а 1-3 самых сильных места для красивых `custom_visual_slot`;
- для каждого слота пишет короткий дизайн-бриф, цель визуала и ограничения;
- все ссылки на блоки и claims потом проверяются машинным валидатором;
- если LLM предложил неизвестный блок или claim, нормализация/валидация не пропускает такой visual дальше.

Итоговая философия: инфографика может быть красивой и свободной по композиции, но не свободной по фактам.
