# Агент-писатель

## Назначение

Писатель — единственный агент, который пишет прозу. Он получает утвержденную структуру, фактуру и проектные знания, а возвращает черновик материала в формате сайта: `{ meta, blocks }`.

Его задача не «написать статью вообще», а заполнить уже спроектированные блоки так, чтобы каждый абзац был связан с фактом, механизмом, ограничением или проверяемой продуктовой возможностью.

## Источники правил

- `handoff-konveyer/02-format.md` — формат итогового документа.
- `handoff-konveyer/03-bloki.md` — структура блоков.
- `handoff-konveyer/04-kachestvo.md` — машинная приемка и требования к содержанию.
- `handoff-konveyer/05-fakty.md` — правила фактов.
- `handoff-konveyer/07-promty.md` — промпт писателя.
- `handoff-konveyer/doc-schema.json` — схема итогового JSON.
- `handoff-konveyer/primer-material.json` — живой пример опубликованного материала.
- `handoff-konveyer/fakty/*.json` — продукт, кейсы, конкуренты, термины, глоссарий, внутренние ссылки.

## Вход

Писатель получает:

- `PipelineRequest`.
- `FactPackage` после машинной приемки фактов.
- `MaterialStructure` после машинной приемки структуры.
- `ProjectKnowledge` или релевантный срез `fakty/*.json`.
- Список допустимых внутренних ссылок.
- Лимиты из `limity.json`.
- При необходимости — пример блока из `primer-material.json` как ориентир формы, а не текста.

## Выход

Писатель возвращает `DraftDoc`:

```json
{
  "meta": {
    "title": "...",
    "seoTitle": "...",
    "description": "...",
    "slug": "...",
    "author": { "name": "Команда Lexis Voice", "kind": "organization" }
  },
  "blocks": [
    {
      "id": "lead",
      "type": "lead",
      "text": "...",
      "sourceClaimIds": ["F1", "F3"]
    }
  ]
}
```

Текущая внутренняя модель `DraftDoc` упрощена относительно `doc-schema.json`, поэтому реализация писателя должна либо:

- возвращать блоки, совместимые с текущим `DraftBlock`; либо
- расширить `DraftBlock` под реальные поля блоков сайта перед подключением публикации.

Для первой версии достаточно первого варианта, но нельзя терять тип блока, заголовки, массивы `items`, `sourceClaimIds` и данные таблиц/steps/faq.

## Главные правила

- Писатель использует только факты из `FactPackage` и `ProjectKnowledge`.
- Факт без источника не добавляется в текст.
- Цифры не округляются и не придумываются.
- Факты про Lexis Voice, продукт, кейсы, интеграции и метрики берутся только из `produkt.json` и `keysy.json`.
- Факты о других продуктах берутся только из `konkurenty.json` или официального сайта самого продукта, если это уже попало в `FactPackage`.
- Термины из `terminy.json` повторяются слово в слово.
- Если термин есть в `glossariy.json`, его не нужно определять заново: лучше поставить внутреннюю ссылку.
- Ссылки в тексте только внутренние и только из `vnutrennie-ssylki.json`.
- Название продукта пишется `Lexis Voice`, не `мы`.
- Нельзя писать превосходные степени про продукт или рынок.
- Нельзя употреблять слово `конкурент` в финальном тексте.

## Лид

Лид — самый важный блок.

Требования:

- 200–450 знаков.
- Отвечает на главный вопрос целиком.
- Не является вступлением.
- Самодостаточен: его можно вырезать и показать отдельно.
- Не начинается с `Это`, `Мы`, `Наш`, `Здесь`, `Поэтому`.
- Без выделений и внутренних ссылок.
- Опирается на `sourceClaimIds`.

Плохой лид: подводит к статье и обещает, что ниже будет ответ.

Хороший лид: уже дает ответ, а ниже раскрывает детали.

## Текст разделов

- Один абзац — одна мысль.
- В каждом смысловом абзаце есть факт, механизм, ограничение, число, источник или проверяемая продуктовая возможность.
- Раздел отвечает на вопрос заголовка, а не пересказывает соседний раздел.
- Если после удаления предложения смысл не меняется, предложение не нужно.
- Границы применимости называются прямо: когда подход не подходит, чего он не решит, какие данные нужны.
- Продукт появляется там, где он является ответом на задачу, и одной-двумя конкретными фразами, а не рекламной вставкой.
- Материал не должен быть универсальным текстом, который можно вставить на сайт другого продукта без замены слов.

## Разметка внутри текста

Разрешен только мини-синтаксис сайта:

```text
**жирный**
==маркер==
__подчеркивание__
//курсив//
[текст](/adres)
```

Правила:

- Не больше двух акцентов на абзац.
- Ссылки только внутренние, начинаются с `/`.
- Ссылки ставятся в потоке текста, а не отдельным списком.
- На другие продукты ссылки не ставятся.
- Заголовки, лид и ячейки таблиц не размечаются.
- HTML и Markdown-структура запрещены.

## Блоки

Писатель заполняет блоки, которые запланировал структурщик.

- `lead` — самодостаточный ответ.
- `tldr` — 3–5 коротких выводов, не дублирующих лид.
- `prose` — вопрос и абзацы ответа.
- `points` — критерии, признаки или ошибки: короткий title + пояснение.
- `steps` — процесс по шагам; каждый шаг имеет действие и результат.
- `table`/`matrix` — данные и сравнение, формулировки короткие и параллельные.
- `cards` — карточки предметов подбора или обзора.
- `fork` — развилка выбора; для `compare` обязательно есть `neither`.
- `verdict` — отвечает на вопрос выбора, не пересказывает статью.
- `quote` — только если есть атрибутируемая цитата.
- `callout` — короткий блок смысла, особенно для news.
- `promo` — внутренняя врезка, если она не ломает чтение.
- `related` — только адреса из внутренних ссылок.
- `faq` — минимум 8 вопросов, ответы длиннее 80 знаков.
- `sources` — источники с датой снимка для внешних фактов.
- `cta` — действие под тему, а не дефолтная кнопка.

## CTA

Дефолтного CTA нет. Писатель заполняет CTA по `plannedCta` из структуры.

Правила:

- CTA должен логически следовать из вопроса материала.
- CTA не обещает результат, которого нет в фактуре.
- CTA не подменяет тему рекламным блоком.
- Если материал про тренировки — CTA может вести к голосовому тренажеру.
- Если материал про найм — CTA может вести к оценке кандидатов или тест-звонку.
- Если материал про контроль качества — CTA может вести к разбору звонков или чек-листам.
- Если нужная возможность продукта не подтверждена, CTA должен быть общим или задача возвращается в `needs_facts`.

## FAQ

FAQ — не пересказ статьи.

Требования:

- Минимум 8 вопросов.
- Каждый вопрос заканчивается `?`.
- Каждый ответ длиннее 80 знаков.
- Вопросы такие, которые человек задает после чтения.
- Хороший FAQ содержит неудобные вопросы: `Можно ли заменить этим руководителя?`, `Когда это не подойдет?`, `Что делать, если данных мало?`.

## Запрещенные признаки машинного текста

Писатель не использует:

- `важно отметить`, `стоит подчеркнуть`, `следует помнить`, `необходимо учитывать`;
- `играет ключевую роль`, `служит напоминанием`, `символизирует`;
- `в современном мире`, `в эпоху цифровизации`, `стремительно развивается`;
- `по словам экспертов`, `отраслевые отчеты показывают`, если источник не назван;
- `в заключение`, `подводя итог`, `резюмируя`;
- частое `не просто..., а...`, `не только..., но и...`;
- подмену субъекта: `этот факт подчеркивает`, `данное обстоятельство свидетельствует`;
- синонимическую кашу: `платформа`, `данное решение`, `инструмент`, `сервис` об одном и том же в соседних абзацах;
- остатки реплик ассистента: `Конечно`, `Надеюсь, это поможет`, `Сообщите, если нужно доработать`.

## Когда возвращать задачу

Писатель не должен героически закрывать дырки текстом.

Возврат в `needs_facts`:

- структура требует факт, которого нет в `FactPackage`;
- нужна продуктовая возможность Lexis Voice, но ее нет в `produkt.json`;
- нужна кейсовая цифра, но ее нет в `keysy.json`;
- нужен факт о другом продукте без источника и даты снимка;
- невозможно написать честный CTA без подтвержденной продуктовой возможности.

Возврат в `needs_structure_revision`:

- блоки не соответствуют теме;
- разделы дублируют друг друга;
- структура не содержит места для границ применимости;
- FAQ спланирован как пересказ разделов;
- CTA противоречит теме.

## Машинная приемка после писателя

После писателя запускается `validateMaterial`.

Минимум проверок:

- `seoTitle <= 65`.
- `description <= 160`.
- `lead` ровно один, первый, 200–450 знаков.
- Объем текста 1200+ слов.
- FAQ 8+ вопросов.
- Compare содержит `fork`, `table`, `verdict`.
- Все `sourceClaimIds` существуют.
- В тексте нет внешних ссылок.
- Все обязательные блоки структуры есть в черновике.

## Промпт писателя

Системная часть должна включать ядро из `07-promty.md` и роль писателя:

```text
Роль: автор отраслевого материала.

Вход: бриф, структура, фактура, список внутренних адресов.
Выход: DraftDoc JSON в формате сайта.

Правила:
- Пиши только по фактам из входа.
- Лид 200–450 знаков и отвечает на вопрос целиком.
- Каждый абзац несет одну мысль и подпирается фактом, механизмом или ограничением.
- Термины из terminy.json не переписываются.
- Ссылки только внутренние и только из списка.
- Возможности Lexis Voice пишутся со статусом из produkt.json.
- О других продуктах — только факты из konkurenty.json или FactPackage.
- Не добавляй HTML, Markdown и внешние ссылки.
- Не используй штампы сгенерированного текста.
```

## Что нужно решить перед реализацией

- Расширять ли `DraftBlock` сразу до полного `doc-schema.json` или оставить текущий упрощенный слой и расширить перед публикацией.
- Нужно ли писателю писать весь материал одним вызовом или по блокам. Для качества и управляемости лучше по блокам, но первая версия может быть одним вызовом с жестким JSON.
